各位老师好，我是汇报人何嘉辉。本次汇报的项目是 G15 预测性维护场景沙盘。我们面向教学实验与工程验证，将工况配置、信号生成、健康分析和结果对账贯通起来，形成可复现的业务流程。项目支持正常、退化和突发故障三类场景，并提供控制台、实验报告与双 Linux 部署能力。下面我从产品、架构、协作和工程验证四个方面介绍项目。

我们的产品以振动和温度信号为输入，通过外置 YAML 配置与固定随机种子构建可复现的工况。正常场景建立健康基线，退化场景反映渐进变化，突发场景刻画明确的风险事件。分析模块提取八类特征，依据规则计算健康分并生成告警。事件真值独立保存，在报告阶段用于结果匹配；规则健康分用于表征当前风险状态，工况、分析和对账形成可追溯的处理链路。

这一页展示了我们围绕设备状态组织的五项产品能力。风险面板配置指定设备的风险类型、强度与持续时间，健康趋势呈现状态变化；总览连接采集、处理和提交进度。波形与频谱支持分析原始信号，实验报告用于比较不同工况的结果。通知配置管理消息通道及发送状态。通过设备标识和运行记录，我们能够从界面上的变化追溯到信号、特征和告警事件。

我们的架构将数据处理主链与平台服务分离。配置模块驱动信号和故障生成，生产者按 NPZ、校验值和 Manifest 发布分片；消费者完成校验、分窗、特征计算和事务写入。SQLite 保存结果与消费进度，报告模块完成真值匹配和指标汇总。持续仿真采用独立 live 协议，控制台通过查询接口读取状态，通知与处置使用独立记录库，各模块以清晰接口协同运行。

我们的分工采用统筹、核心技术和专项子系统三个层次。A 负责需求、架构与集成；B1 负责仿真和性能，B2 负责分析与评分。C1 至 C4 分别承担故障、持久化、配置和接口职责，C5 的职责是测试矩阵、故障验证、指标对账与报告生成，C6 负责部署和运维。协作通过需求分解、功能分支、非作者评审、CI 和固定版本复验推进，最终交付已由 PR 178 合入主线。

现场演示将围绕同一设备的一次完整运行展开。本页提供 Windows 本机与双 Linux 虚拟机入口。在 Linux 标签中，我们可以分别启动 Ubuntu 和 RHEL，也可以同时启动两个系统；控制器等待目标服务就绪后打开对应看板。每台系统独立运行十台仿真设备，使用同一交付版本。我们先观察采集、提交与健康趋势，再为指定设备配置风险强度、延后时间和持续时间，跟踪风险发生与结束。随后演示单设备暂停、任务排空和恢复采集，验证序号连续性。最后关联波形、特征与报告，使用停止入口排空任务并保留运行记录。项目服务的启停与虚拟机电源分开管理，重复启动会复用当前会话。 本次已在两台虚拟机实际完成启动、重复启动、停止、立即重启和再次停止；停止后四个隧道端口全部关闭。最终通过本页重新启动，两个看板各显示十台设备。

我们在 Ubuntu 24.04.5 和 RHEL 9.7 上完成验证，两系统均为 2075 项通过、15 项跳过。百万点生产管线各执行三轮，最大耗时分别为 0.310 秒和 0.241 秒，计时覆盖数据生成至完整发布。故障验证包括坏分片拒收，以及提交一片后强制终止进程、重放剩余六片并完成五表对账。七份软件工程报告覆盖可行性、需求、设计、测试和双系统部署。 最终部署采用持久目录和用户级 systemd 服务，SSH 断开后继续运行。两份部署报告已更新为 V3.1，各十九页，记录 Windows 页面启停、虚拟机桌面入口和完整循环实测。

这次项目使我们将性能、恢复和交付要求落实为可执行规则。性能检查采用未舍入耗时严格小于 60 秒的门禁；恢复检查从进程重启进一步落实到逐表内容一致；评审与测试结果绑定具体交付版本。独立效果验收与查询容量评估仍是后续改进重点，当前尚未形成通过结论。我们将继续完善独立验证流程、查询负载模型和设备接入方案，使系统能力在明确条件下得到持续验证。 部署联调还发现两个问题：转发端口不同触发 Host 校验，统一两端端口后解决；停止后立即重启的端口预检查报错，通过 SO_REUSEADDR 修复并完成复测。服务输出追加到持久日志，使 RHEL 上的启动故障也能直接定位。

以上是 G15 预测性维护场景沙盘的项目汇报。我们通过本次实践，将可控仿真、健康分析、数据恢复与工程交付连接起来，也形成了围绕需求、接口和验证结果开展协作的方法。感谢老师在需求分析、设计和验证过程中的指导，感谢团队成员的投入与协作。接下来我将结合系统架构、现场演示和验证报告回答各位老师的问题。Thank you for your attention.
