# 答辩后增补：维护建议知识库

本增补以答辩冻结版 `936c127` 为基线，已于 2026-11-18 经人工评审后通过
[PR #180](https://github.com/Zhu-ShuH/g15-predictive-maintenance/pull/180) 合入 `main`（`ae0bdc7`）。
它不改写答辩冻结版或其验证记录，不代表完成独立验收或验证十万并发；
课程最终成绩及教师最终验收结果未记录。

## 所在层与作用

知识库放在告警之后的维护建议层，不放入健康评分公式，也不属于真值对账层。
实际链路为：特征 → 健康评分及扣分原因 → 去抖告警 → 匹配维护知识 → 人工检查建议。
总分只说明风险程度；相同分数可能由不同特征造成，不能直接从低分推断轴承故障。
既有红黄告警级别决定处置优先顺序，知识库解释相应扣分特征应复核哪些项目。

冻结版已有硬编码建议。本次将八类检查映射抽成一个独立、版本化、可追溯的
JSON 知识源 `src/g15/knowledge/maintenance.json`。JSON 是用键和值记录结构化
数据的文本格式。条目目前是课程示例，不是厂商手册或经过现场验证的诊断规则。
原始来源明确标为冻结版的检查映射，不能把迁移到知识库等同于提升工业可信度。

## 数据与关系

知识库：schema_version、version、scope、source_id、source、example_only。
知识条目：id、feature、action、basis。一本知识库包含多条知识条目。
每条知识以一个已知特征为触发条件，匹配条件是已存告警原因中该特征风险大于 0，
且不超过 1；只接受有限数值。未知特征、非法数值、缺失证据不生成具体检查项。

一次知识匹配保留 entry_id、knowledge_version、source_id、source、example_only、
action、basis 和 evidence。evidence 保存告警规则、窗口位置、级别、特征、值、
风险及原始原因。一个告警可以匹配多个条目，同一条目可以被多个告警匹配。
它们是**文件实体和派生对象，不是新增 SQL 表**；原有 SQLite 表和外键均不改变。
窗口的精确分数仍以原数据库为准；告警 reason 内数值经过格式化，不当作完整精度原始特征。

例如：告警 `drivers: rms=2 (risk 0.9)` 匹配 `KB-003`，建议复核振动 RMS、
传感器安装、紧固与负载变化。页面和通知显示条目编号、版本及课程示例标识，
页面显示完整来源。红色活动告警仍要求现场人员按规程判断，不自动停机。

## 接线与更新

Python `g15.knowledge.catalog.match_knowledge` 负责纯匹配；
`notifications.advice.maintenance_advice` 保留原签名和通用兜底。
运营回放告警增加只读 `knowledge_matches`；当前维护建议页使用相同知识源的
静态投影，并保留分页、来源缺失及历史/活动状态边界。

修改 JSON 后执行 `python tools/build_maintenance_catalog.py`，更新浏览器投影。
自动测试核对两个文件内容相同，防止前后端规则漂移。规则随软件包版本发布，
不运行时联网、不调用大模型、不读取 `private_truth`、不新增设备控制或工单动作。
后续要用厂商规则，必须补齐设备型号、适用工况、手册版本/章节、审核记录，
通过独立规则审查后再扩展；当前 schema 故意只允许 example_only=true。

既有告警按当前知识版本产生展示建议，而非追溯伪造历史时点建议。通知已冻结
正文维持原有队列语义；页面的派生匹配没有另建历史快照表，不宣称长期不可变审计。

## 验证范围

单测覆盖条目溯源、非法数值、未知特征、零风险、重复驱动、来源缺失、
版本与前端数据一致性；整仓回归与真实浏览器结果另附实际执行记录。
不以此补充视为双 Linux 新版实测、独立工业验收或真实设备维护验证。

## 只读知识库页面

控制台导航“维护知识库”进入 `/knowledge`，显示全部 8 条规则、适用条件、建议、判断依据、来源、版本和适用范围。维护建议中的“查看规则 KB-xxx”跳转到对应条目。页面读取同一生成的知识目录，不依赖已有告警，不提供编辑或设备执行操作。
