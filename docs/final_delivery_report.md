# G15 期末项目交付报告

## 从设备信号到可追溯的维护判断

G15 是面向预测性维护教学的场景沙盘：用户通过配置生成正常、退化和突发故障数据，在控制台观察设备状态、健康趋势和告警，再用同一运行的报告核对结果。项目把数据生成、独立消费、分析、持久化和报告连成可运行闭环，并以完整性校验、事务恢复和实际性能测试验证关键工程指标。

```mermaid
flowchart LR
    A[场景与风险配置] --> B[仿真采集]
    B --> C[NPZ与完整Manifest]
    C --> D[独立消费与健康分析]
    D --> E[SQLite与审计]
    E --> F[控制台、告警与报告]
```

本次交付整改由 [#177](https://github.com/Zhu-ShuH/g15-predictive-maintenance/issues/177) 跟踪，代码与文档提交在 [PR #178](https://github.com/Zhu-ShuH/g15-predictive-maintenance/pull/178)。受测产品版本为 `16d57df485d428c02914bac372b61c67917857da`；后续文档证据修订与该产品版本分开标记。正式合并仍以最终head的真实非作者批准和CI为条件。

## 现场展示的四个结果

| 用户要完成的事 | 已有能力 | 展示方式 |
|---|---|---|
| 看见设备正在发生的变化 | 多设备实时仿真、采集进度、设备状态与健康趋势 | 总览选择设备，展示真实计数和趋势更新 |
| 用参数构造不同工况 | YAML外置配置、正常/退化/突发事件和仿真风险控制 | 对照配置和实际输出，源码保持一致 |
| 从告警追到原因 | 窗口特征、评分规则、级别与时间定位、JSON/Markdown报告 | 打开同一设备、同一运行的告警和报告 |
| 在故障后恢复并核对结果 | 坏分片拒收、事务一致性、重复消费幂等、Linux强杀恢复 | 显示失败原因、恢复步骤与逐表一致性证据 |

答辩按“业务问题→架构与分工→现场演示→复盘与贡献”展开。[12页、12分钟讲稿](presentation.md)给出逐页主题、真实演示步骤和失败回退路线；原始日志与审查细节作为备查材料。

## 性能门禁修复

原基准命令能够给出耗时，但成功退出只证明完整性，没有自动约束60秒门槛。本次让正式三轮脚本显式启用 `--max-production-seconds 60`，按未舍入生产时间严格判断。恰好60秒、超时或非法计时均失败；三轮输出与CLI/日志写入退出码全部保留，任何一轮失败都会使总验收失败。

本次没有改变数据规模、计时窗口、评分算法或阈值。百万点表示1,000,000个采样时刻、两个信号共2,000,000个标量，包含生成、序列化、SHA计算、文件写入和complete Manifest发布；校验与CLI总墙钟分别解释。

质量证据已完成：Windows提交前工作树2067项通过、23项跳过；同产品树的Python3.11/3.12 CI各2075项通过、15项跳过；Black共146文件通过，Pylint分别为Windows9.68/10、CI9.67/10。[测试报告§14](test_report.md)与[CI记录](https://github.com/Zhu-ShuH/g15-predictive-maintenance/actions/runs/43676377920)保存版本和实际范围，不把跳过项目计作通过。

双Linux新克隆验收也已完成：Ubuntu和RHEL各2075项通过、15项跳过；百万点三轮均严格小于60秒，Ubuntu中位数0.279秒、最大0.310秒，RHEL中位数0.236秒、最大0.241秒。两系统的README演示入口、配置A/B、坏数据拒收和真实SIGKILL五表恢复对账均通过。RHEL完整验收隔离外网；Ubuntu完整验收正常网络，另有内核禁网的核心流程与demo证据。详见[本轮实测](delivery_validation_20261115.md)，其中明确基准RSS与基准CLI总墙钟未测。

## 设计取舍与对比证据

文件接口用完整Manifest和摘要区分“数据已经写完”和“目录已经出现”；消费端用同一事务保存结果与进度，强杀后通过重放和逐表核对证明恢复正确。评分过程不能读取真值，真值只在报告层用于对账。对应取舍与限制可从[架构](architecture.md)、[持久化ADR](adr/0005-analysis-persistence-contract.md)和[独立验证协议](adr/0006-independent-validation-protocol.md)追溯。

查询优化保留过同机、同数据、每态50次的三态对照：未ANALYZE约23.575秒，ANALYZE后约0.020秒，再加复合索引约0.013秒，见[查询ADR的原始记录与边界](adr/0007-user-query-capacity-and-validation.md)。它说明查询计划对统计信息敏感；这是历史合成单库实验，不能外推为当前多run拓扑或100k成绩。真实查询p95/EXPLAIN观察及Gate0失败保留在[测试报告§10](test_report.md)，本次没有重跑容量工作。
