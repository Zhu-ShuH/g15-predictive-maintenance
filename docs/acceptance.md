## 2. 百万点与 60 秒

- 一个点是一个采样时刻，即一个 seq；1,000,000 点含振动和温度各 1,000,000 个值，共 2,000,000 个信号标量。seq 与时间戳不计为信号标量。
- 固定 seed=42、sample_rate_hz=100、total_points=1000000、chunk_points=102400；完整输出 10 个 NPZ 分片（9×102400 + 78400）及完整 Manifest。信号与故障参数采用提交入库的 benchmark_1m.yaml 并记录摘要，禁止临场删减数据或改用空数组。
- 用 time.perf_counter 计时：配置校验完成后、第一次生成数据之前开始；包括随机初始化、趋势/噪声/故障生成、序列化、文件写入、SHA-256 及最后 complete Manifest 原子发布；发布完成并关闭文件后结束。这里的落盘指应用文件写入完成，不宣称断电持久性或强制硬件刷盘。
- 排除环境安装、配置解析、下游消费、特征分析和报告生成；这些阶段另报耗时。Python 解释器启动耗时不计入，CLI 总墙钟耗时另列，不得混用。
- 每个系统在独立空运行目录连续测 3 次，保留全部结果；3 次均须严格 <60 秒，同时给出中位数、最大值和峰值内存（未测内存则写未测）。仅测算法内核不能代替完整生产基准。
- 验证输出点数、类型、连续序号、哈希与 complete 清单；计时结束后的独立校验耗时另列，生成时计算哈希包含在生产时间内。

## 3. 受控故障与误报

100% 指下面预定义教学测试集上的事件召回率，不代表真实设备准确率。开发 seed=42；验证 seed=20261016 不参与阈值调参。先提交配置、评分规则和测试预期，再执行验证；失败保留记录，不为过关临时放宽阈值。

固定用例轮廓：单设备，100 Hz、window_points=256、chunk_points=10240、total_points=65536、incomplete_window=drop；两个信号基线/噪声分别为 0.5/0.05 g、35/0.15 degC。正常场景退化率为 0，无故障；退化场景将振动退化率改为 0.00002 g/采样，检查后半段健康分中位数低于前半段，误报警不按正常数据门槛判定。

| 用例 | 注入设置 | 通过条件 |
|---|---|---|
| 正常 | 无事件；两个 seed 分别运行 | 告警数为 0；事件召回率为 null，不填 100% |
| spike | 单事件，start_seq=16384、duration_points=256、amplitude=5.0 | 对应事件被检出 |
| step | 单事件，start_seq=16384、duration_points=2048、amplitude=5.0 | 对应事件被检出 |
| burst | 单事件，start_seq=16384、duration_points=2048、amplitude=5.0 | 对应事件被检出 |

三类故障各在两个 seed 上运行，共 6 个应检事件，必须 TP=6、FN=0。事件类型对波形的具体作用沿用 C1/B1 经评审的故障定义，不在验证器里重造注入算法；受控测试使用连续触发窗数 N=1，N>1 的去抖、升级、恢复另做边界测试，不能用 N=1 冒充去抖已验证。评分权重、黄红阈值与其他规则由 B2 提交候选，C5 在验证前记录规则版本和开发集结果，A 审核后固定；本文不伪造尚未提交的规则配置。

匹配细则：

1. 真值事件为半开区间 [s,e)，仅独立验证器读取；consumer/analysis 不读取故障配置、位置或 private_truth。
2. 窗口长 W=256；事件允许告警窗口起点区间为 [floor(s/W)×W, ceil(e/W)×W + 2W)。即覆盖事件相交窗口，并允许结束后最多 2 个窗口的宽限；max_detection_lag_windows=2。使用告警数据窗口 start_seq，不用机器当前时间。
3. 必须同 device_id；有效黄/红告警按 (device_id,rule_id,start_seq) 去重。事件与告警一对一匹配，先求最大匹配数，多解按事件起点、event_id、告警起点、rule_id 排序选择；一条告警不能算检出多个事件。
4. detection_rate=TP/事件总数；零事件返回 null。列出逐事件匹配、漏报、首次告警窗口、数据时延和宽限。检测输出不得填入真值 event_id，匹配由验证器产生。
5. false_alarm_count 为不落入任一事件允许窗口的告警数，正常场景所有告警均为误报。故障窗口内重复告警另列 redundant_alarm_count；未匹配告警总数另列 unmatched_alarm_count，不能将多次正常触发隐去。故障场景报告误报数，当前通过门槛为受控正常场景 0 误报及 6/6 事件检出。

这些固定轮廓由 C3 写入授权 configs/*.yaml、B2 提交 health_rules.yaml、C5 在 #9 转成可执行测试并记录配置摘要；实现未提交前保持“待执行”。若实际波形定义导致用例不适用，应在首次验证前提交理由供 A 评审，留下版本变更记录。

## 4. 解耦、恢复及工程门禁

- 仿真和消费分别在独立进程执行，通过 NPZ/Manifest 文件接口交换，禁止共享仿真对象或全局变量；不要求实时网络接口。保留 simulate 与 consume 独立运行日志。
- 改 YAML 的退化率、故障率、seed 后运行结果按预期变化，源码 SHA 不变；非法配置明确失败。字段与 CLI 契约仍按 interface.md 评审。
- 正常、退化、突发三场景生成 JSON + Markdown 闭环报告；真实覆盖特征→健康分→告警→SQLite→报告，未知数据写 null。
- 至少 15 个有意义的单元测试、20 个可执行用例；至少三类独立故障注入证据：业务故障、SHA/文件损坏、Linux kill -9 恢复。业务三种波形不替代后两项可靠性测试。
- 重复消费不增加重复窗口/告警；kill -9 后与未中断运行的窗口、评分、告警和持久状态一致。状态、窗口、告警和 processed_chunks 同事务，具体状态字段仍待 B2/C2 评审。
- Black、Pylint≥8.5、pytest 实际通过；CI 和人工 Review 满足后合并。依赖未锁定、脚本占位、缺任何双 Linux 记录时不得声明最终交付完成。
