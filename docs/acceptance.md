## 0. 评分基线与诚实状态

六个评分维度及红线的逐项状态、责任人与证据入口见
[期末评分、标准与红线追踪矩阵](compliance.md)。本项目按 9 人 L3 候选组织材料，但
“平台化/多协议/分布式考量”只有在 #135/#136 的真实实现与 Gate 证据完成后才计入已实现范围；
ADR 或容量目标本身不等于功能完成。

终验状态只有三种：

- **已有可核证据**：仓库中能定位实现、测试、PR/Review 或历史原始记录；仍须在最终候选 SHA 复验。
- **待固定 SHA 复验**：已有能力，但本轮尚未在同一最终提交及规定环境执行。
- **待实现/待人工完成**：缺实现、独立数据、资源、人工 Review 或现场行为；严禁写成通过。

本标准不预估分数。教师现场故障注入、答辩抽题、个人讲解和加分认定均只能在现场发生，仓库只准备可复现实物与演练材料。

## 1. 验收环境与交付

公开 GitHub 仓库；从可行性、需求、设计到实现、测试、部署、运维、复盘形成证据闭环。Ubuntu 24.04 LTS 与 Red Hat Enterprise Linux 9 分别使用虚拟机或实体机，在同一个 Git 提交上全新克隆、安装、运行。正式环境为 Conda pp03 / Python 3.12，步骤见 environment.md。Python 3.11 CI 仅为额外兼容检查，不能代替 RHEL 实测。

两系统分别留下：提交 SHA、配置/规则版本与摘要、系统版本、CPU、内存、存储、Python/NumPy/Conda 版本、命令、退出码、日志和报告。答辩日期未定，D1–D14 仅相对排期。现场安装网络由 C6 提前检查并准备经测试的备用依赖；现场仍须展示从公开仓库下载运行。

## 2. 百万点与 60 秒

- 一个点是一个采样时刻，即一个 seq；1,000,000 点含振动和温度各 1,000,000 个值，共 2,000,000 个信号标量。seq 与时间戳不计为信号标量。
- 固定 seed=42、sample_rate_hz=100、total_points=1000000、chunk_points=102400；完整输出 10 个 NPZ 分片（9×102400 + 78400）及完整 Manifest。信号与故障参数采用提交入库的 benchmark_1m.yaml 并记录摘要，禁止临场删减数据或改用空数组。
- 用 time.perf_counter 计时：配置校验完成后、第一次生成数据之前开始；包括随机初始化、趋势/噪声/故障生成、序列化、文件写入、SHA-256 及最后 complete Manifest 原子发布；发布完成并关闭文件后结束。这里的落盘指应用文件写入完成，不宣称断电持久性或强制硬件刷盘。
- 排除环境安装、配置解析、下游消费、特征分析和报告生成；这些阶段另报耗时。Python 解释器启动耗时不计入，CLI 总墙钟耗时另列，不得混用。
- 每个系统在独立空运行目录连续测 3 次，保留全部结果；3 次均须严格 <60 秒，同时给出中位数、最大值和峰值内存（未测内存则写未测）。仅测算法内核不能代替完整生产基准。
- 验证输出点数、类型、连续序号、哈希与 complete 清单；计时结束后的独立校验耗时另列，生成时计算哈希包含在生产时间内。

## 3. 受控故障与误报

100% 指下面预定义教学测试集上的事件召回率，不代表真实设备准确率。开发 seed=42；验证 seed=20261016 不参与阈值调参。先提交配置、评分规则和测试预期，再执行验证；失败保留记录，不为过关临时放宽阈值。

固定用例轮廓：单设备，100 Hz、window_points=256、chunk_points=10240、total_points=65536、incomplete_window=drop；两个信号基线/噪声分别为 0.5/0.05 g、35/0.15 degC。正常场景退化率为 0，无故障；退化场景将振动退化率改为 0.00002 g/采样，检查后半段健康分中位数低于前半段，误报警不按正常数据门槛判定。

| 用例 | 注入设置 | 通过条件 |
|---|---|---|
| 正常 | 无事件；两个 seed 分别运行 | 告警数为 0；事件召回率为 null，不填 100% |
| spike | 单事件，start_seq=16384、duration_points=256、amplitude=5.0 | 对应事件被检出 |
| step | 单事件，start_seq=16384、duration_points=2048、amplitude=5.0 | 对应事件被检出 |
| burst | 单事件，start_seq=16384、duration_points=2048、amplitude=5.0 | 对应事件被检出 |

三类故障各在两个 seed 上运行，共 6 个应检事件，必须 TP=6、FN=0。事件类型对波形的具体作用沿用 C1/B1 经评审的故障定义，不在验证器里重造注入算法；受控测试使用连续触发窗数 N=1，N>1 的去抖、升级、恢复另做边界测试，不能用 N=1 冒充去抖已验证。评分权重、黄红阈值与其他规则由 B2 提交候选，C5 在验证前记录规则版本和开发集结果，A 审核后固定；本文不伪造尚未提交的规则配置。

匹配细则：

1. 真值事件为半开区间 [s,e)，仅报告层（`reporting.builder`/`reporting.metrics`）读取用于真值对账；consumer/analysis 及 `reporting.verifier` 不读取故障配置、位置或 private_truth。
2. 窗口长 W=256；事件允许告警窗口起点区间为 [floor(s/W)×W, ceil(e/W)×W + 2W)。即覆盖事件相交窗口，并允许结束后最多 2 个窗口的宽限；max_detection_lag_windows=2。使用告警数据窗口 start_seq，不用机器当前时间。
3. 必须同 device_id；有效黄/红告警按 (device_id,rule_id,start_seq) 去重。事件与告警一对一匹配，先求最大匹配数，多解按事件起点、event_id、告警起点、rule_id 排序选择；一条告警不能算检出多个事件。
4. detection_rate=TP/事件总数；零事件返回 null。列出逐事件匹配、漏报、首次告警窗口、数据时延和宽限。检测输出不得填入真值 event_id；匹配由报告层（`reporting.builder` / `reporting.metrics`）产生，`reporting.verifier` 与 `g15 verify` 不读真值。
5. false_alarm_count 为不落入任一事件允许窗口的告警数，正常场景所有告警均为误报。故障窗口内重复告警另列 redundant_alarm_count；未匹配告警总数另列 unmatched_alarm_count，不能将多次正常触发隐去。故障场景报告误报数，当前通过门槛为受控正常场景 0 误报及 6/6 事件检出。

这些固定轮廓由 C3 写入授权 configs/*.yaml、B2 提交 health_rules.yaml、C5 在 #9 转成可执行测试并记录配置摘要；实现未提交前保持“待执行”。若实际波形定义导致用例不适用，应在首次验证前提交理由供 A 评审，留下版本变更记录。

## 4. 解耦、恢复及工程门禁

- 仿真和消费分别在独立进程执行，通过 NPZ/Manifest 文件接口交换，禁止共享仿真对象或全局变量；不要求实时网络接口。保留 simulate 与 consume 独立运行日志。
- 改 YAML 的退化率、故障率、seed 后运行结果按预期变化，源码 SHA 不变；非法配置明确失败。字段与 CLI 契约仍按 interface.md 评审。
- 正常、退化、突发三场景生成 JSON + Markdown 闭环报告；真实覆盖特征→健康分→告警→SQLite→报告，未知数据写 null。
- 至少 15 个有意义的单元测试、20 个可执行用例；至少三类独立故障注入证据：业务故障、SHA/文件损坏、Linux kill -9 恢复。业务三种波形不替代后两项可靠性测试。
- 重复消费不增加重复窗口/告警；kill -9 后与未中断运行的窗口、评分、告警和持久状态一致。状态、窗口、告警和 processed_chunks 同事务，具体状态字段仍待 B2/C2 评审。
- Black、Pylint≥8.5、pytest 实际通过；CI 和人工 Review 满足后合并。依赖未锁定、脚本占位、缺任何双 Linux 记录时不得声明最终交付完成。

## 6. 新评分标准新增门禁

### 6.1 可靠性与现场注入

教师可能现场注入断网、坏数据或强杀进程。候选版本必须预先固定每类故障的注入点、期望失败、降级/补偿动作、恢复命令和对账判据：

- **断网**：依赖安装完成后，离线主链不得访问网络；断网不等于安装源不可用。禁网 demo/verify 尚须在最终 SHA 留证。
- **坏数据**：SHA/Schema 失败必须拒收，不把部分结果标可信；保留错误和未写入/已提交边界。
- **进程强杀**：区分 `kill -9`、普通异常和断电；只对真实测过的层级作承诺。重启后以已提交态恢复，并与不中断基线逐表对账。
- **补偿**：当前补偿是拒收、幂等重放、重新消费或显式人工 reset，不包含自动停机或设备控制。

### 6.2 安全与工业数据红线

- 当前产品没有密码登录或密码持久化；不得为了展示 PBKDF2 凭空增加账号系统。若后续引入口令，先审公共契约，再使用 PBKDF2-HMAC 或等效强哈希、随机盐和恒时比较，禁止明文进入 YAML、Git 或日志。
- 当前 `state_json` 信封本身非 append-only；独立 append-only 审计链已由 #143/#147 落地，UPDATE/DELETE/REPLACE 被触发器拒绝并通过 C4 非作者复核。应用级“只增不改”已满足；文件级防篡改仍未声称，拥有文件/DDL 权限者可替换数据库，尾锚/尾缀删除不可检。
- 运行只使用本地仿真/派生数据；真实工业数据不得进入公开仓库、测试 fixture、第三方 AI 或未授权外发。外发前必须有字段允许列表、脱敏结果、授权人、用途和期限记录。
- 本项目没有真实设备执行器，只告警、不下发停机。未来真实设备接入必须另立变更单，采用只读旁路和回退方案，并由两位非作者复核；任何停机/维护动作必须人工确认与审计。
- `reset-alarms --yes --reason ...` 是告警状态重置的人工确认，不得描述为设备停机确认或安全审计已经完备。

### 6.3 软件工程与文档门禁

- 生命周期、需求、测试和文档四件套分别参照 GB/T 8566-2022、GB/T 9385-2008、GB/T 15532-2008、GB/T 8567-2006，具体映射见 `docs/compliance.md`；“参照”不等于认证。
- PEP 8、Black 与 Pylint≥8.5 是最低代码门禁；测试数量必须是真实、有效用例，不能以参数化计数或重复包装刷数量。
- `main` 只接收 feature/docs/fix/test 分支的 PR；至少一位非作者批准且 CI 通过。每周提交频率、commit 数、PR/Review 和子系统实物共同构成贡献证据，不允许刷 commit。
- README、可运行仓库、一键脚本和单元测试属于扣分红线；脚本失败必须非零退出，不能用预生成 `runs/` 或 PPT 代替现场运行。

### 6.4 技术深度与 L3 门禁

现有 ADR、百万点、恢复对账只能支撑已实测的结论。查询/容量扩展须在 #135 的真实服务落地后，由 #136 在固定 SHA 和 D0 真实 SQLite 上保存独立 oracle、冷热 `EXPLAIN QUERY PLAN`、p50/p95/p99、吞吐、错误、资源和计数守恒。高负载逐档重新授权；未执行不得写 100k 已通过。

## 7. 最终候选版本冻结

最终候选 SHA 必须同时满足：

1. R01–R10 逐条给出命令、阈值、实际结果、证据路径和责任人；#56→#9 的独立保留集正式完成。
2. Black、Pylint、pytest、文档引用和 CI 对同一 SHA 通过，失败/skip 原因不隐藏。
3. Ubuntu 24.04 与 RHEL 9 对同一 SHA 完成 clean clone、安装、demo、verify、benchmark、断网/坏数据/强杀演练。
4. append-only 审计已由 #143/#147 落地并通过 C4 非作者复核；安全审计红线在应用级“只增不改”上满足，文件级防篡改仍不声称。
5. README、四件套、运行手册、复盘、贡献表和答辩材料完成，九位成员分别确认自己的子系统讲解与真实贡献。
6. 现场记录新证据时只追加命令、原始结果与结论，不回写或覆盖失败证据。
