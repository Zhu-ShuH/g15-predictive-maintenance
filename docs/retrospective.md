# G15 项目复盘

> 复盘基线：`main@997acaebef2d4ab72639954afe8078bd9a04452b`，2026-11-10。
> 本文只记录仓库、Issue、PR、测试报告中可核对的事实。尚未完成的教师现场注入、
> 独立保留集、查询容量和 Release 复证保持“待完成”，不以计划代替结果。

## 1. 项目目标与当前阶段

G15 的目标是用可复现仿真完成预测性维护教学闭环：配置退化和故障，生成带摘要的数值分片，由独立消费者计算特征、健康分和告警，使用 SQLite 保证幂等恢复，最后生成 JSON/Markdown 报告并在报告层与隔离真值对账。

截至本基线，核心主链、坏数据拒收、真实 Linux `kill -9`、百万点双 Linux 基准、依赖锁和 `reset-alarms` 已有实现或既有证据。项目仍处于终验收口阶段，不能宣称最终完成：

- #56 → #9 的真正独立保留集尚未冻结并首次执行；
- #135 查询服务和 #136 Gate 0/p95/`EXPLAIN QUERY PLAN` 尚未实现或实测；
- 现有 reset 历史位于可更新状态行，尚不满足独立 append-only 审计红线；
- 最终候选 SHA 仍需重新做一键、禁网和双 Linux 证据冻结；
- C5 本人可核验交付、全员每周提交频率等贡献硬项仍有真实缺口。

## 2. 做得好的地方

### 2.1 把“可运行”拆成可证伪的契约

- NPZ 四列 dtype/长度/路径和 Manifest 摘要形成文件接口，生产与消费可独立运行。
- Manifest 最后发布，消费者只接受 `complete`；坏片、缺片、跨片不连续或摘要冲突明确失败。
- 报告把 `false_alarm_count`、重复和未匹配告警、不可判定 `null` 分开，避免只展示漂亮百分比。

### 2.2 恢复不是一句“有 WAL”

- 特征窗口、告警、告警状态和 `processed_chunks` 同片同事务提交。
- 真实 Linux SIGKILL 用例验证“部分前缀已提交、其余回滚、重放后五表逐行等价”，没有只比行数。
- 同片同 SHA 幂等跳过、同片异 SHA 拒绝，防止输入被替换后静默复用旧结果。

### 2.3 证据边界逐步变严格

- Windows、CI、Ubuntu、RHEL、压力 opt-in 和正式验收分别记录，不再用一个平台的结果代填另一个平台。
- 百万点计时从内核扩展为生成、序列化、写入、SHA 和 complete Manifest 的完整生产窗口。
- Review 绑定精确 head；新提交后旧批准失效，避免“改完仍沿用旧票”。

### 2.4 决策有 ADR 和回退边界

文件解耦、随机性、恢复/独立验证、持久化信封、查询容量都留下 ADR 或契约记录。对于 100k 查询，没有在资源和量测未可信前直接跑高负载，而是拆为真实查询路径与分级 Gate。

## 3. 主要踩坑、根因与修正

以下每项都包含“原先为什么不够”和“以后怎样防止复发”，作为至少五项真实复盘证据。

### 3.1 把内核速度当成完整生产性能

**问题**：早期快数只覆盖数组计算，不能证明分片、写盘、摘要和 Manifest 在 60 秒内完成。

**根因**：指标名称相同，但计时起止点没有被冻结。

**修正**：在 `docs/acceptance.md` 固定 1,000,000 点、两路信号、10 分片、计时窗口和三轮统计；benchmark 同时输出生产与独立校验时间。

**防复发**：性能结论必须带配置摘要、机器、解释器、SHA、三轮原始值、中位数/最大值和峰值内存；只测内核只能标“子阶段”。

### 3.2 真值读者职责一度混乱

**问题**：“验证器读取真值”曾被写成泛化口径，容易让完整性校验器与报告层混为一谈。

**根因**：把“验证”同时用作文件完整性检查和检测效果对账。

**修正**：冻结为 `reporting.verifier/g15 verify` 只读 Manifest/NPZ；只有 `reporting.builder/metrics` 在检测结果形成后读取 `private_truth` 做对账，consumer/analysis 永不读答案。

**防复发**：代码、角色文件、test plan 和 roadmap 使用相同术语；新增 reader 必须做真值路径扫描和非作者 Review。

### 3.3 报告曾把冲突片的两套统计混在一起

**问题**：摘要冲突时，处理点数排除问题片，但分析窗口/告警仍可能计入，出现负丢弃点或失真的检出率。

**根因**：数据库原始记录和“可归属当前 Manifest 的有效记录”没有分层。

**修正**：按分片范围过滤有效窗口和告警，同时保留 raw/excluded 计数；以恒等式和变异测试证明不是 `max(0, ...)` 掩盖错误。

**防复发**：任何对账指标都先定义集合，再做计数；原始、排除、有效三者必须满足守恒关系。

### 3.4 SQLite 只读/WAL 竞态不能靠重试口号解决

**问题**：错误分类和连接时序可能把 `SQLITE_ERROR`、`BUSY` 与真正 `READONLY` 混为一类，观察者/写者启动竞态也会造成偶发误判。

**根因**：只看异常文本或宽泛 `OperationalError`，没有检查 SQLite 主/扩展错误码与实际文件状态。

**修正**：分离只读入口、按错误码分类、加入独立探针与固定 SHA 重复验证；写者校验 WAL 句柄可写性。

**防复发**：恢复策略必须区分“可重试”“配置/权限要修”“输入已损坏”，并保留失败上下文，不能把所有数据库错误包装成同一句话。

### 3.5 `kill -9` 用例最初不够强

**问题**：固定 sleep 或仅比最终行数，不能证明信号真的落在中间态，也不能发现同数不同内容。

**根因**：为了容易自动化，弱化了故障时机和结果对照。

**修正**：子进程真实 SIGKILL；父进程轮询已提交前缀，断言未完成；重放后对五表排序逐行比较。

**防复发**：故障测试必须证明“故障确实发生、发生在目标阶段、恢复内容等价”，三项缺一不可。Windows 无 SIGKILL 时明确 skip。

### 3.6 依赖锁“有文件”不等于可复现安装

**问题**：版本锁、Python 3.11/3.12 marker、build isolation 和项目安装步骤若混在一条命令，可能在新机失败。

**根因**：只关注依赖列表，没有验证 clean install 的命令顺序和 `pip check`。

**修正**：锁安装与项目 `--no-deps --no-build-isolation` 分两步，再执行 `pip check`；Ubuntu/RHEL 分别 fresh clone 留证。

**防复发**：每次改依赖、构建配置或 setup 脚本，都要在干净环境验证，已有开发环境成功不能代替。

### 3.7 Shell 行尾、权限和运行环境会破坏“一键”

**问题**：Windows checkout 的 CRLF、脚本执行位、路径假设或把测试临时目录放进受监控工作区，都可能导致换机失败或权限残留。

**根因**：在单一开发机验证，没有把文件模式、行尾、临时目录和 shell 差异视为接口。

**修正**：统一 LF/可执行位、相对路径与 `set -euo pipefail`；测试临时目录放到业务仓库之外的系统临时目录，失败时保留明确路径和退出码。

**防复发**：clean clone 验收必须覆盖 checkout 后的真实文件模式；清理脚本只允许受控目标，不以扩大删除范围处理权限问题。

### 3.8 先说“100k”再定义负载，会得到错误结论

**问题**：并发用户、在途请求、连接数、虚拟用户和累计请求数容易被混用；关闭式吞吐上限也可能被写成固定 offered load。

**根因**：先定宣传数字，后补同步窗口、客户端/服务端计数、缓存和资源模型。

**修正**：ADR-0007 区分 Profile F/H、client/server in-flight、D0/D1/D2 和逐档授权；#135 先做真实查询，#136 再做 oracle/计数/容量。

**防复发**：没有固定查询契约、独立 oracle、资源授权、p95/p99 和 `EXPLAIN QUERY PLAN` 时，不运行或外推高负载。

### 3.9 可恢复审计不等于 append-only 审计

**问题**：`reset_history` 能在正常更新和重开库后保留，但它仍位于可 UPDATE 的状态行，不满足“只增不改”的安全红线。

**根因**：运维可追溯与安全不可篡改被当作同一个等级。

**修正计划**：独立 Issue/ADR 设计 INSERT-only 事件、拒绝 UPDATE/DELETE 的数据库约束和篡改失败测试；在完成前明确标红，不以文档改名冒充实现。

**防复发**：安全性质必须有逆向测试（尝试修改/删除应失败），不能只验证正常路径能读到历史。

## 4. 没做好的协作问题

### 4.1 状态文档更新落后于 main

README、architecture、deployment、operations、test report 的时间点不同，旧“未实现/待 G4”文字可能在功能合入后仍保留。根因是功能 PR 没有把所有事实来源列为 DoD。

改进：以 `docs/acceptance.md`/Issue 追踪为总入口；Release 候选做一次“实现—文档—测试—证据”四向扫描，历史表标明基线而不覆写。

### 4.2 独立验证职责发生转派

C5 本人尚无可核验独立 PR，相关任务转由 B1 承接。转派保证了项目推进，但不能把 B1 的交付改署为 C5，也不能满足“人人有真实贡献”的评分硬项。

改进：答辩前按实际团队确认成员；仍在组的成员必须补真实、有意义、可讲述且经 Review 的交付，不以空 commit 或文档签名补数量。

### 4.3 PR 很多，但“同一最终 SHA”仍要重证

分阶段证据证明当时的功能，但后续合并会改变树。最终验收必须在同一个候选 SHA 复跑质量门禁、闭环、性能、禁网和双 Linux；不能拼接不同 SHA 的最好结果称一次完整通过。

## 7. 可复用原则

1. 先冻结“怎样判定”，再运行；结果不好也保留。
2. 设计性质要有反例测试：真值隔离靠路径扫描，append-only 靠修改失败，恢复靠真实强杀。
3. 每个数字都带单位、范围、机器、SHA 和采集阶段。
4. 同一词只表达一种职责：完整性校验不等于效果验收，历史可读不等于不可篡改。
5. 自动化证据优先，但不能替代独立人工 Review、真实设备安全门禁或现场答辩能力。
