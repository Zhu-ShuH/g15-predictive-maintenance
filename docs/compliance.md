## 3. 行业红线判定

| 红线 | 当前判定 | 项目边界与必须动作 |
|---|---|---|
| 密码不得明文存储 | **当前不适用，但必须守卫** | 当前产品不提供密码登录、不持久化密码。#135 若引入口令，必须先审契约并采用 PBKDF2-HMAC/等效强哈希、独立随机盐和恒时比较；密码、token、派生材料不得进入 YAML、Git 或日志 |
| 审计日志 append-only | **已满足（应用级只增）** | 独立 `audit_events` 表 + 三触发器已由 #143/#147 落地，UPDATE/DELETE/REPLACE 被拒，C4 非作者复核通过。`state_json` 仍是可变业务副本；文件级防篡改未声称（拥有文件/DDL 权限者可替换库，尾锚/尾缀删除不可检） |
| 工业数据不出域；外发脱敏与授权 | **部分满足** | 主链运行时离线、仓库只含仿真数据；任何日志/报告外发前必须走数据分级、字段允许列表、脱敏、授权人与用途/期限登记。真实厂区数据不得进入公开仓库、fixture 或第三方 AI |
| 真实设备变更单、旁路接入、双人复核 | **当前架构不适用** | 本项目是教学沙盘，没有真实设备适配器或执行器。未来接入真实设备前必须另立变更单、只读旁路、回退方案并由两位非作者复核；未完成前禁止接入 |
| 误停执行须人工确认 | **当前架构不适用，禁止自动执行** | 系统只产生健康分/告警，不下发停机。`reset-alarms` 需 `--yes` 和原因，但它也不是停机命令。任何未来停机/维护动作必须独立授权、人工确认与审计 |
| README、一键运行、单元测试、可运行仓库 | **已有实物，待最终 SHA 复验** | README、setup/demo/verify/benchmark 和测试已存在；只有 clean clone 的真实命令/退出码与 CI 才能证明终验通过 |
| Git/贡献真实性 | **流程已有，个人证据待冻结** | `main` 仅经 PR、至少一位非作者批准；最终贡献表用 `git shortlog`、PR/Review 与子系统交付交叉核验。不得刷 commit 或用 A 内部复核重复计作独立评审 |

## 5. 发布判定

只有同时满足以下条件，才能将候选 SHA 标为“期末终验候选”：

1. 需求追踪中每个必选项都有命令、阈值、实际结果、证据路径与责任人；未通过项不隐藏。
2. Black、Pylint≥8.5、pytest、文档引用和 CI 对同一 SHA 通过。
3. Ubuntu 24.04 与 RHEL 9 clean clone 对同一 SHA 完成安装、demo、verify、benchmark 和现场故障演练。
4. #56→#9 独立验收完成；#135 已实现（#149），#136 若列入 L3 已实现范围，则必须按 Gate 真实通过。
5. append-only 审计红线已完成独立实现（#143/#147）与 C4 非作者 Review；应用级“只增不改”满足，文件级防篡改仍不声称。
6. 贡献表、答辩材料与个人讲解由真实成员确认；A/自动化代理不能代替人工签字、教师评分或个人答辩。
