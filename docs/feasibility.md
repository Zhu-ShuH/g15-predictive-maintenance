# G15 可行性分析与阶段风险

> Issue [#2](https://github.com/Zhu-ShuH/g15-predictive-maintenance/issues/2)；负责人 A；2026-10-28；实现快照 main `75b119454a1ac075620bdcc74826730fa7b4ac02`。这是基于现有实物的阶段判断，不是会议纪要、接口冻结或最终验收结论。

## 1. 目标与已有基础

面向无真实退化设备的教学答辩，构建可配置仿真—独立消费—特征/评分/告警—验证报告闭环；交付公开仓库、现场新克隆运行及 Ubuntu 24.04 LTS/RHEL 9 两套独立证据。范围与标准沿用 [requirements](requirements.md)、[acceptance](acceptance.md)，环境沿用 Conda pp03 / Python 3.12，Python 3.11 只作兼容 CI。

早期“主线只有仿真内核”的描述已过期：配置/validate（#26/#55）、故障（#27）、文件协议和生产入口（#29/#30/#43/#48）、分析（#54）、消费与 SQLite（#64）均已合入。共享类型迁移 #31 已完成；#53 已留下 Windows 完整百万点生产记录。对应 PR 与主线追踪入口见 [requirements](requirements.md)。

仍缺的是完整命令链和正式交付证据：主线除 validate 外 CLI 仍占位，报告模块为空，scripts 仍失败退出；#67/#70–#73/#76 是待评审或待整改候选，不能当作已经集成。双 Linux、真实强杀、依赖锁定与独立保留验证仍须补齐。

## 3. 范围取舍

必须交付趋势/噪声、可控故障、配置外置、公开文件接口、特征/健康分/告警、独立真值验证、报告、错误诊断、恢复与双 Linux 运行。可视化在核心链路通过后再决定。真实设备接入、训练模型、RUL、微服务和在线 AI 不是本期前置。

需求与验收标准不在本次调整。一个点仍为一个采样时刻，双信号标量数另报；百万点计时包括生成与完整发布。受控集召回、误报和时延沿原标准；已暴露开发数据与独立保留验证分开，不为得到通过记录先选新 seed、删失败或修改阈值。
